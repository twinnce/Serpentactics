# Serpentactics — журнал разработки

## Архитектурные решения

### [дата: 07.2026] Изометрия реализуется через 3D, а не 2D

**Решение:** несмотря на то, что игра визуально выглядит как 2D пиксель-арт,
внутри сцена — полноценная **3D**, с ортографической камерой
(Camera3D / Orthogonal), направленной под 45°.

**Обоснование (две независимые причины, указавшие на один и тот же выбор):**

1. **Визуальный стиль.** Целевой эффект — "дышащая" картинка: чёткие
   непересекающиеся пиксели, но с плавным микро-движением спрайтов/клеток
   между ходами (idle-анимации, лёгкое покачивание змеи и т.п.).
   Такой эффект получают через пайплайн:
   3D-сцена → рендер в SubViewport низкого разрешения → Nearest-фильтрация
   при масштабировании на экран. Плавная 3D-анимация "схлопывается" в
   пиксельную сетку каждый кадр заново, создавая органичное "дыхание",
   которое нереально нарисовать вручную в 2D без огромного объёма
   покадровой анимации.

2. **Механика высоты поля (0–2 уровня) + динамическое изменение поля
   картами.** В 2D порядок отрисовки объектов на разных уровнях высоты
   требует ручной модификации Y-sort и постоянного пересчёта при каждом
   изменении поля картами — особенно сложно для змеи, которая физически
   растянута через несколько клеток разной высоты одновременно.
   В 3D порядок отрисовки (z-buffer) решается автоматически движком,
   включая частично перекрывающие друг друга объекты на разных высотах.

**Практическое следствие:** внутреннее "пиксельное" разрешение —
это не настройка проекта, а SubViewport фиксированного низкого размера
внутри сцены (например, ориентир ~480×270), настраивается при создании
сцены поля/камеры, отдельно от разрешения окна.

## Настройки проекта (зафиксированные решения)

- **Stretch Mode:** `canvas_items` — сохраняем текущее значение.
- **Stretch Aspect:** `expand` — сохраняем текущее значение.
  Даёт адаптацию под любые пропорции экрана без искажений и без
  чёрных полос: на широких экранах открывается больше игрового поля
  по горизонтали.
  **Дизайн-следствие:** UI должен крепиться к краям экрана (anchors),
  а не к фиксированным координатам; фон должен быть достаточно большим
  или бесшовно тайлящимся, так как разные игроки видят разное количество
  игрового пространства вокруг основного поля.
- **Base Viewport (Display → Window → Size):** явно выставить `1920×1080`
  (сейчас не задано явно — используется скрытый дефолт движка).
- **Default Texture Filter (Rendering → Textures → Canvas Textures):**
  переключить на `Nearest` — обязательно для чёткого пиксель-арта.

## Технический спайк: подтверждение пайплайна 3D → пиксель-арт

**Статус: подтверждено практикой (07.2026).** Собран минимальный прототип
(несколько тестовых 3D-фигур с разными idle-анимациями через
AnimationPlayer) — эффект "дыхания" картинки при чётких непересекающихся
пикселях подтверждён визуально. Архитектурное решение (см. выше) считается
проверенным, можно строить реальную архитектуру поверх него.

**Нюансы, всплывшие при сборке спайка (важно для будущих сцен):**

- **SubViewport внутри SubViewportContainer не позволяет вручную задать
  Size** — контейнер сам управляет размером viewport'а. Правильный способ
  задать внутреннее низкое разрешение — свойство контейнера
  **Stretch Shrink** (делитель), а не Size у самого SubViewport напрямую.
  Пример: при экране 1920×1080 и Stretch Shrink = 4 внутренний рендер
  получается ~480×270.
- **Texture Filter может быть переопределён локально** на узле
  (SubViewportContainer → CanvasItem → Texture Filter) поверх глобальной
  настройки проекта — при создании подобных узлов в будущем проверять,
  что стоит Inherit или явно Nearest, иначе глобальный Nearest не сработает
  для этой конкретной картинки.
- **Без DirectionalLight3D все грани сливаются** — только ambient-свет
  недостаточен для восприятия объёма. DirectionalLight3D выбран осознанно
  (не Omni/Spot), т.к. даёт одинаковое затенение объекта независимо от его
  позиции на игровом поле — важно для консистентного плоского стиля.
- (**На заметку, не решено**) Материал по умолчанию (StandardMaterial3D)
  использует PBR-освещение — вероятно, слишком "реалистично" для плоского
  пастельного стиля из GDD. При переходе от тестовых фигур к настоящим
  ассетам — обсудить unshaded/toon-подобные материалы отдельно.

### [дата: 07.2026] Топология поля — квадратная сетка

**Решение:** игровое поле использует классическую квадратную сетку
(4 направления), а не гексагональную.

**Обоснование:** рассматривались оба варианта. Гексагональная сетка дала бы
более симметричные тактические паттерны для карт-способностей (кольца,
конусы, прямые линии по 6 направлениям), но:
1. Смещает жанровую идентичность дальше от классической Змейки
   (4-направленное движение — часть узнаваемого "ощущения" жанра).
2. Требует отдельной системы координат (axial/cube), что добавило бы
   третью независимую ось сложности одновременно с уже принятыми
   сложными механиками (3D-пайплайн, высота поля, динамическое изменение
   поля картами).

Топология сетки — фундаментальное решение, которое дорого менять
постфактум (пронизывает движение, карты, процедурную генерацию, хранение
координат), поэтому зафиксировано осознанно, а не оставлено "на потом".

### [дата: 07.2026] Механика обновления поля между уровнями

**База:** поле не пересоздаётся с нуля — существующий уровень **обрастает
новым регионом**, и при этом **до половины клеток, с которыми игрок
взаимодействовал картами** (не способностями змеи), могут быть
заменены/изменены генератором. Без предварительного телеграфирования —
риск встроен в сам факт использования карты на клетку, а не объявляется
заранее.

**Обоснование:**
- "Только добавление, без изменений" отвергнуто — старые регионы
  становятся полностью предсказуемыми, что даёт игроку возможность найти
  безопасный маршрут и эксплуатировать его бесконечно, подрывая ключевое
  напряжение жанра Змейки (сокращение безопасного пространства по мере
  роста).
- Телеграфирование (заранее показывать, что изменится) отвергнуто —
  если игрок заранее знает, какие клетки под угрозой, он просто не будет
  вкладывать в них карты, и риск перестаёт быть риском.
- Ограничение "не более половины тронутых картами клеток" — верхняя
  граница потерь для игрока, чтобы усилия никогда не обнулялись
  полностью.
- Риск привязан **только к клеткам, изменённым картами**, не к базовому
  передвижению змеи — жертва честная, потому что это следствие
  добровольного решения игрока сыграть картой, а не случайная кара.
  Тематически стыкуется с задумкой скинов-классов (см. открытые
  вопросы): карты — "временная внешняя магия", подверженная риску;
  врождённые способности скина — часть змеи, риску не подвержены.

**Правила безопасности генератора (гарантии независимо от рандома):**
- Клетки в радиусе 1 от каждой клетки тела змеи не могут быть изменены
  генератором ("защитный буфер").
- Всегда должен существовать минимум один путь (кольцо) от головы до
  хвоста змеи — гарантия, что у игрока всегда есть безопасный маневр,
  что бы ни сгенерировалось.
- Если генерация оставляет врагов/особые клетки недостижимыми —
  генератор прокладывает к ним тропу принудительно (случайным образом).
- Скрытые внутренние "якоря" — точки, которые генератор гарантированно
  делает достижимыми, не раскрывая эту механику игроку — обеспечивают,
  что на карте всегда есть куда идти.

**Направление роста поля (выбор игрока):** когда уровень зачищен, на
каждом из 4 направлений от текущей границы освоенной территории
появляется иконка-превью, показывающая примерное содержимое региона
(тип региона — снег/лава/острова/вода/лес/обычное поле и т.п.,
преимущественный тип врагов, наличие босса) — без раскрытия точной
раскладки клеток. Игрок выбирает направление осознанно, зная общий
профиль риска/награды, но не детали исполнения. Дополнительно —
отдельная кнопка "рост во все стороны сразу": более сильное изменение
существующего поля (сильнее правила "до половины"), но и заметно
большая награда — даёт игроку контроль над темпом эскалации хаоса в
игре в течение забега.

**Открыто на будущее (сознательно не решаем сейчас):**
- Точный механизм "до половины" — детерминированное правило или
  вероятностный шанс, в среднем дающий половину.
- Конкретное усиленное правило изменения поля для кнопки "во все
  стороны" (по аналогии с "до половины", но строже).
- Как именно направления отличаются по риску/награде — на уровне
  геймдизайна ещё не определено, только сам принцип, что они должны
  различаться.

## Открытые вопросы (добавление)

- **Скины змеи как классы.** Разные скины (бронированная, классическая,
  анаконда, робот-змея, змея без чешуи и т.д.) — классы с уникальными
  killer-способностями, задуманы так, чтобы прохождение всей игры
  естественно вынуждало пробовать разные скины, а не искать единственный
  оптимальный билд (осознанная борьба с эффектом "игрок выбирает
  оптимальную стратегию, даже если ему скучно"). Не спроектировано
  подробно. Ключевой риск на будущее: балансировка, чтобы ни один скин не
  стал объективно доминирующим.

### [дата: 07.2026] Модификаторы клеток — компонентная архитектура

**Решение:** модификатор клетки — не единая иерархия наследования по
типу поведения, а **композиция независимых поведенческих компонентов**.
Базовый Resource-тип модификатора хранит общие данные (имя, иконка,
описание) и список прикреплённых компонентов поведения (блокирует
проход, наносит урон при входе, изменяет движение, пассивный визуальный
эффект и т.п.). Игровая логика опрашивает активные модификаторы клетки
на наличие нужного типа компонента, не зная конкретный тип модификатора.

**Обоснование:**
- Один модификатор может сочетать сразу несколько видов влияния
  одновременно (например, "горящие шипы" = блокировка + урон) — обычное
  наследование "один тип = одна ветка" не позволяет это выразить чисто.
- К релизу ожидается порядка 100 конкретных модификаторов при примерно
  10 категориях поведения — композиция позволяет собирать большинство
  новых модификаторов из уже существующих переиспользуемых компонентов,
  а не писать код заново для каждого.
- Неизвестно заранее, появятся ли новые категории поведения в будущем —
  архитектура не требует знать полный список типов влияния сразу:
  новая категория добавляется как новый независимый компонент, без
  правки существующих модификаторов или компонентов.

## Реализованная архитектура (08.2026)

### Система модификаторов клеток — реализация

Архитектурное решение (композиция компонентов) описано выше, зафиксирована
реализация:

- `resources/cell_modifiers/cell_modifier_component.gd` — `CellModifierComponent`,
  базовый пустой класс-Resource, служит "меткой типа" для наследников.
- `resources/cell_modifiers/cell_modifier.gd` — `CellModifier`, контейнер
  (`display_name`, `icon`, `description`, `components: Array[CellModifierComponent]`),
  методы `get_component`/`has_component` через `is_instance_of`.
- `resources/cell_modifiers/components/` — конкретные кирпичики:
  `BlocksPassageComponent` (пустой, факт блокировки — булево состояние),
  `DamageOnEnterComponent` (`damage: int`, урон применяется один раз, в момент
  входа на клетку — **не каждый ход стояния на клетке**; см. открытый вопрос
  ниже про будущий "урон за каждый ход").
- `resources/cell_modifiers/instances/` — собранные через инспектор `.tres`:
  `fire.tres`, `burning_spikes.tres`.

**Соглашение по именованию компонентов:** `[Глагол 3-го лица][Объект]Component`
(например `BlocksPassageComponent`, `DamageOnEnterComponent`) — класс должен
читаться как утверждение о том, что делает компонент, при подстановке в
`is_instance_of`. Слова выбираются по точности границ эффекта, не по общности
(`Passage` — конкретно вход в клетку, не `Movement` — иначе занял бы место
будущего компонента "заморозка/стан", который блокирует движение змеи в целом,
а не конкретную клетку).

**Правило new-компонент vs новое-поле:** разное количество/значение (урон,
тип урона) → новое поле в существующем компоненте. Разное поведение/логика
(например, ледяной урон ещё и замораживает) → новый отдельный компонент.

**Переиспользование ресурсов:** клетки на разных координатах поля, использующие
один и тот же `.tres`-модификатор, хранят ссылку на **один и тот же объект**
в памяти (стандартное поведение Godot `Resource` без `resource_local_to_scene`).
Это даёт "бесплатно" будущую механику карт вида "весь огонь +1 урон" —
достаточно изменить одно поле у одного объекта ресурса, эффект применится
сразу ко всем клеткам, ссылающимся на него. При проектировании генератора
поля отдельно решить: клетки с одинаковым модификатором продолжают шарить
один ресурс, или для part-по-клеточной кастомизации нужны независимые копии
(`duplicate()`).

### Система поля

- `scenes/field/cell.gd` — `Cell extends RefCounted`. Хранит `grid_position`,
  `modifier: CellModifier`. **Не хранит** `is_occupied_by_snake` — этот факт
  единственно хранится в `Snake.body`, вычисляется через `snake.is_occupying()`
  (см. принцип "единственный источник истины" ниже).
- `scenes/field/field.gd` — `Field extends RefCounted`. `cells: Dictionary`
  (ключ `Vector2i`, значение `Cell`) — выбран `Dictionary`, а не 2D-массив,
  ради поддержки полей произвольной формы (острова/впадины из GDD) без
  дыр-заглушек. Методы: `get_cell` (безопасно, через `.get(key, null)`),
  `has_cell`, `set_cell` (add+перезапись одним методом — присваивание по
  существующему ключу в `Dictionary` перезаписывает автоматически),
  `remove_cell` (через `cells.erase()`).
- `scenes/field_generator.gd` — `FieldGenerator extends RefCounted`,
  статический метод `generate_rectangle(width, height)`. Намеренно упрощённый
  генератор (просто прямоугольник без модификаторов) — полноценная процедурная
  генерация с островами/якорями/защитным буфером отложена до появления
  реального геймплея, на котором её можно тестировать.

### Система змеи и движения

- `scenes/snake/snake.gd` — `Snake extends RefCounted`. `body: Array[Vector2i]`,
  **`body[0]` = голова**, последний элемент = хвост (зафиксировано осознанно;
  математически расход на insert(0)/pop_back() эквивалентен альтернативе
  push_back()/pop_front(), выбор сделан исключительно по читаемости кода,
  не по производительности — на масштабе змеи в десятки клеток разница
  неощутима). `health: int`, `take_damage()`. Методы `get_head_position()`,
  `get_tail_position()` (через `body[-1]`), `is_occupying(position)`.
- `scenes/snake/movement_resolver.gd` — `MovementResolver extends RefCounted`,
  два статических метода:
  - `can_move(snake, field, direction) -> bool` — проверяет существование
    клетки, `snake.is_occupying()` (защита от самопоглощения), `BlocksPassageComponent`.
  - `apply_move(snake, field, direction) -> void` — применяет `DamageOnEnterComponent`,
    затем `body.insert(0, target)` + `body.pop_back()`.
  Разделены по SRP: "можно ли" и "применить последствия" — разные причины
  для изменения кода.
- `scenes/snake/gameplay_controller.gd` — `GameplayController extends Node`
  (обязательно `Node`, не `RefCounted` — только `Node` участвует в игровом
  цикле и получает `_unhandled_input`). Хранит текущие `snake`/`field`,
  слушает `_unhandled_input`, вызывает `MovementResolver`.
  `Input.is_action_just_pressed` (не `is_action_pressed`!) — нужно ровно одно
  движение на одно нажатие, не серия движений на удержание клавиши.

**Input Map — соглашение по именованию направлений:** действия называются
по сторонам света **в системе координат поля** (`move_north`/`move_south`/
`move_east`/`move_west`), не по экрану (`move_right` и т.п.). Причина:
`MovementResolver` и вся логика поля ничего не знают о повороте камеры на 45° —
это отдельный уровень абстракции (визуальный), и он не должен просачиваться
в логику. Конкретное сопоставление клавиш (WASD/стрелки) → конкретное
действие — сознательно оставлено временным до появления реальной камеры
на сцене; будет пересмотрено по ощущениям, когда появится картинка.

**Открытый вопрос — геймдизайн, не архитектура:** обнаружено во время
тестирования, что текущая логика всегда трактует попытку входа в клетку
собственного хвоста как самостолкновение (`is_occupying` проверяется до
движения, до того как хвost физически "освобождает" клетку через `pop_back()`
в этот же ход). Это может быть намеренным дизайн-решением или пограничным
случаем, который потребует отдельного разрешения (аналогично классическим
играм-змейкам, где это частый предмет дискуссии) — не решено, оставлено
как есть до дальнейшего продумывания.

**Открытый вопрос — система раундов и множественных ходов (из более
позднего уточнения GDD, 08.2026):** в полной версии — раунд состоит из
розыгрыша карт (в любой момент) + нескольких ходов движения (стандартно 3;
skins-"быстрые змеи" стартуют с большим количеством; карты могут добавлять
временные или перманентные ходы). Скорость змеи, вероятно, станет полем
`.tres`-ресурса скина. **Текущая упрощённая реализация: один ход = одно
движение**, `GameplayController` этого не учитывает — сознательно отложено
до появления системы карт/раундов, которую можно будет реально протестировать.

### Единственный источник истины (single source of truth)

Применяется последовательно везде, где факт мог бы задублироваться:
"занята ли клетка" не хранится в `Cell`, только в `Snake.body`, вычисляется
по требованию. Тот же принцип должен соблюдаться и для будущего визуального
слоя — визуал **только отображает** `Field`/`Snake`, никогда не хранит
параллельное собственное состояние игровой логики.

### Визуализация (3D, пиксель-арт пайплайн — первая интеграция)

- `scenes/field/grid_utils.gd` — `GridUtils extends RefCounted`. Статические
  утилиты перевода "логика поля" → "визуал": `grid_to_world(grid_position) -> Vector3`
  (`CELL_SIZE = 1.0`; ось Y логики поля → мировая ось **Z**, мировая ось Y
  зарезервирована под будущую высоту — сейчас всегда `0.0`), `is_dark_tile(grid_position) -> bool`
  (шахматный узор через `(x + y) % 2`, без хранения — вычисляется на лету).
  **Используется `Vector2i`/`Vector3i` только для дискретных индексов,
  `Vector2`/`Vector3` — для непрерывных мировых величин** (позиции узлов
  всегда `Vector3`, даже при целочисленном `CELL_SIZE`, — обязательное
  требование Godot, плюс задел под будущее плавное "дыхание" картинки
  между клетками).
- `resources/materials/` — `light_tile_material.tres`, `dark_tile_material.tres`
  (`StandardMaterial3D`) — авторские редактируемые данные, не хардкод цвета в коде.
- `scenes/field/cell_visual.tscn`/`cell_visual.gd` — `CellVisual extends MeshInstance3D`.
  `BoxMesh` с малой высотой (не `PlaneMesh` — нужны видимые боковые грани для
  различимости границ сетки при направленном свете). Метод `setup(grid_position)`
  выставляет `position` через `GridUtils.grid_to_world` и `material_override`
  через `GridUtils.is_dark_tile`. Материалы через `preload`+`const` (не `load`
  в цикле) — избегаем повторной работы при создании множества клеток.
- `scenes/field/field_visualizer.gd` — `FieldVisualizer extends Node3D`.
  Метод `build(field)` перебирает `field.cells` (перебор `Dictionary` даёт
  **ключи**), инстанцирует `CellVisual` на каждую координату через `.instantiate()`.
- `scenes/common/pixel_render_rig.tscn` — вынесенный из `main.tscn` переиспользуемый
  риг (Control → SubViewportContainer → SubViewport → Camera3D + DirectionalLight3D
  + пустой узел-слот `WorldContent` типа `Node3D` для внешнего наполнения).
  Переиспользуется через `.instantiate()` + `find_child("WorldContent")`
  (композиция, не Inherited Scene — последовательно с выбором композиции
  над наследованием во всём проекте). Компромисс: поиск по имени строкой
  хрупкий (тихо вернёт `null` при переименовании узла в риге) — рассмотреть
  unique name (`%WorldContent`) при следующей правке этой части.
  `main.tscn` не тронут, остаётся как референс тестового спайка idle-анимаций.

**Визуал модификаторов клеток — принятое направление на будущее, не
реализовано:** по аналогии с поведенческой композицией, визуал модификатора
тоже должен собираться из независимых визуальных "кирпичиков" (своя сцена/
анимация на каждый модификатор или даже на каждый компонент поведения),
а не отдельная сцена на каждую комбинацию. Сознательно отложено до появления
первого реального модификатора с готовым артом — сейчас нет содержимого,
на котором эту систему можно было бы спроектировать и проверить не абстрактно.

### Тестовые сцены — разграничение по роли

- `scenes/tests/field_test.tscn` — изолированная проверка только генерации
  поля (`FieldGenerator`), без змеи/визуала.
- `scenes/tests/gameplay_test.tscn` — изолированная проверка только правил
  геймплея (движение, блокировка, урон, самопоглощение) через `print`
  в консоль, без визуала. Быстрый способ проверить логику независимо от
  рендера.
- `scenes/tests/game_test.tscn` — интеграционная playtest-сцена: поле + змея +
  ввод + полный визуальный пайплайн вместе, "мини-версия реальной игры".
  Не путать по роли с `gameplay_test` — разные инструменты для разных целей,
  сознательно не объединены в один файл.

### Прочие соглашения по именованию

- `[Утилита]Utils` — класс, группирующий несколько статических функций без
  общего состояния, связанных общей темой (например `GridUtils`).
- Static vs обычный метод: если метод не обращается ни к одному полю своего
  же класса (кроме параметров) — кандидат на `static`. Если обращается к
  `self`-полю (неявно) — обязан быть обычным методом.
- Классы — существительные (`FieldGenerator`, не `GenerateField`).

## Визуализация змеи (08.2026, продолжение сессии)

- `scenes/snake/snake_segment.tscn`/`snake_segment.gd` — `SnakeSegment extends MeshInstance3D`.
  `BoxMesh`, размер сознательно меньше `CELL_SIZE` по X/Z (например `0.8 × 0.6 × 0.8`) —
  зазоры между сегментами видны намеренно, подчёркивают дискретность тела
  (соответствует данным — `body` это массив дискретных координат, не непрерывная
  линия). **Отложено сознательно на будущее:** сделать змею визуально непрерывной,
  без зазоров — не реализовывать, пока не появится причина (чисто эстетическая
  доработка, не блокирует тестирование логики).
  Свой `snake_material.tres` (не переиспользует материалы клеток).
  `setup(grid_position)` дополнительно поднимает сегмент по мировой оси Y
  (`HEIGHT_OFFSET`) поверх результата `GridUtils.grid_to_world()` — так, чтобы
  низ сегмента точно касался верха клетки: `HEIGHT_OFFSET = (высота_клетки / 2)
  + (высота_сегмента / 2)`. Это единственное место в коде, где Y-компонента
  результата `grid_to_world` переопределяется — намеренно **не** в самой
  `GridUtils`, так как подъём нужен только сегментам змеи, не клеткам поля.
- `scenes/snake/snake_visualizer.gd` — `SnakeVisualizer extends Node3D`.
  `build(snake)` создаёт по одному `SnakeSegment` на каждый элемент
  **текущего** `snake.body` в момент вызова — **не отслеживает изменение
  длины тела**. Когда будет реализован рост/уменьшение змеи (карты размера
  из GDD) — обязательно вернуться сюда и добавить создание/удаление сегментов
  по мере надобности, сейчас сознательно не реализовано (нет сценария для
  тестирования, т.к. `MovementResolver.apply_move` пока не меняет длину).

### Синхронизация визуала змеи через сигналы Godot

`Snake` объявляет `signal moved` (сама декларация — не логика движения, это
просто способность оповещать; `Snake` по-прежнему не принимает решений о
движении). Сигнал **испускает** `MovementResolver.apply_move()`, сразу после
прямого изменения `body` — единственное место, где реально происходит
изменение и есть доступ к конкретному экземпляру `snake`. `SnakeVisualizer`
подписывается через `snake.moved.connect(_sync.bind(snake))` — `.bind()`
нужен, т.к. сигнал объявлен без параметров, а `_sync()` требует `snake`
явным аргументом. Слабая связанность: `Snake` не знает о существовании
визуализатора, испускает сигнал "вслепую" для любых будущих подписчиков.

**Важный урок по отступам GDScript (баг, пойманный в этой сессии):**
вызов `_sync(snake)` и `snake.moved.connect(...)` должны стоять **на уровне
отступа `for`**, не внутри его тела — иначе `_sync` вызовется на первой же
итерации, когда ещё не все сегменты созданы (`Out of bounds` на массиве
`segments`), и подписка на сигнал задублируется на каждую итерацию.

## Единственный источник истины — распространение на визуал (важный урок сессии)

Обнаружено на практике: `setup()` любого визуального узла (`CellVisual`,
`SnakeSegment`) **полностью перезаписывает** `position` при каждом вызове
(включая повторные вызовы через `_sync` при движении) — значит **ручная
правка `position` прямо в `.tscn`-файле через инспектор не имеет смысла**,
она будет молча затёрта при следующем запуске игры. Любая постоянная
корректировка позиции (например, `HEIGHT_OFFSET` у змеи) обязана быть
зашита в код `setup()`, а не в данные сцены — иначе она не переживёт первый
же вызов синхронизации визуала с данными.
